# polling زمان‌بندی‌شدهٔ Telegram روی همان WordPress — نسخهٔ 1.6.4

## چرا این حالت اضافه شد؟

در حالت وب‌هوک، Telegram باید درخواست POST ورودی به WordPress بفرستد. اگر مسیر ورودی از شبکهٔ Telegram تا هاست ناپایدار باشد، صف pending و خطای timeout باقی می‌ماند، حتی اگر WordPress بتواند با `getMe` به Telegram درخواست خروجی بفرستد. نسخهٔ 1.6.4 یک مسیر جایگزین کم‌هزینه دارد: خود WordPress هر دقیقه با HTTPS و `getUpdates` از Telegram update می‌گیرد. در این روش دریافت update به POST ورودی Telegram وابسته نیست و VPS جدا لازم نیست.

این روش **همچنان به Cron Job و ارتباط خروجی PHP به `api.telegram.org` وابسته است**؛ پاسخ معمولاً تا یک بازهٔ Cron تأخیر دارد و هنگام backlog ممکن است چند بازه طول بکشد. اگر Cron یا دسترسی خروجی Telegram روی هاست کار نکند، این نسخه هم نمی‌تواند آن محدودیت را دور بزند.

## منطق و نگه‌داری داده

- WP-Cron هر دقیقه رویداد polling را اجرا می‌کند. برای زمان‌بندی منظم، Cron Job پنل هاست باید `wp-cron.php?doing_wp_cron` را فراخوانی کند.
- درخواست `getUpdates` از WordPress به Telegram خروجی است؛ حداکثر دو update در هر نوبت دریافت می‌شود تا اجرای Cron هاست اشتراکی کوتاه بماند.
- هر payload ابتدا با کلید یکتای `update_id` در جدول صف موجود WordPress ذخیره می‌شود. فقط پس از ذخیرهٔ updateها، offset در گزینهٔ non-autoload همان دیتابیس جلو می‌رود؛ بنابراین پاسخ Telegram که قبلاً ذخیره شده دوباره پردازش نمی‌شود.
- یک update بلافاصله در همان اجرای Cron پردازش می‌شود تا فرمان تازه بی‌جهت تا اجرای بعدی منتظر نماند؛ updateهای دیگر صف‌گذاری می‌شوند. خطا، آخرین اجرای Cron و آخرین دریافت موفق در پیشخوان قابل مشاهده‌اند.
- اطلاعات آثار/هنرمندان در دیتابیس WordPress باقی می‌ماند. دیتابیس موازی یا فایل دادهٔ تازه ساخته نمی‌شود.

## راه‌اندازی بدون Terminal

1. افزونهٔ v1.6.4 را از WordPress → افزونه‌ها نصب/جایگزین کنید.
2. در DirectAdmin → **Cron Jobs**، از پنل Cron Job بخواهید `https://ahangban.ir/wp-cron.php?doing_wp_cron` را هر یک دقیقه فراخوانی کند. اگر رابط کاربری command می‌خواهد، پشتیبانی هاست می‌تواند Cron را تنظیم کند؛ لازم نیست فرمانی را در Terminal اجرا کنید.
3. در پیشخوان → **آهنگ‌بان API** → «تنظیمات غیرحساس ربات»، حالت **polling زمان‌بندی‌شدهٔ WordPress (بدون VPS)** را انتخاب و ذخیره کنید.
4. در بخش «دریافت پیام‌های Telegram»، روی **حذف وب‌هوک** بزنید. افزونه با `drop_pending_updates=false` وب‌هوک را حذف می‌کند؛ updateهای منتظر حذف نمی‌شوند.
5. با «آزمون اتصال و وضعیت وب‌هوک»، آخرین زمان اجرای Cron، زمان دریافت موفق، خطای polling و صف داخلی WordPress را بررسی کنید. سپس `/start` را بفرستید.

## تفسیر وضعیت

- **Cron polling هنوز اجرا نشده است:** Cron Job فراخوانی نشده، زمان‌بندی WordPress نصب نشده یا درخواست Cron به WordPress نمی‌رسد.
- **آخرین اجرای Cron تازه است اما دریافت موفق ثبت نشده/خطای `getUpdates` وجود دارد:** خروجی HTTPS PHP به Telegram یا ثبت‌بودن وب‌هوک قبلی را بررسی کنید. اگر وب‌هوک باقی مانده باشد، Telegram استفاده از `getUpdates` را رد می‌کند.
- **آخرین دریافت موفق تازه است و صف محلی خالی است:** polling در اجرای اخیر از Telegram پاسخ موفق گرفته و موردی اکنون در صف نیست؛ فرمان تازه را آزمایش کنید.
- **صف محلی رشد می‌کند یا سن آن زیاد می‌شود:** workerهای WP-Cron باید اجرا شوند؛ Cron Job زمان‌بندی‌شده را با پشتیبانی هاست بررسی کنید.

برای همان Bot Token، **فقط یک دریافت‌کننده** فعال باشد: وب‌هوک WordPress، polling زمان‌بندی‌شدهٔ WordPress، یا Python polling روی VPS. هم‌زمانی آن‌ها می‌تواند باعث conflict شود.

## معیار پذیرش و محدودیت راستی‌آزمایی

- Payload پیش از جلو رفتن offset به دیتابیس موجود WordPress نوشته شود.
- retryهای Telegram به‌واسطهٔ `update_id` پیام را دوباره پردازش نکنند.
- حذف وب‌هوک updateهای pending را پاک نکند.
- خطای getUpdates و زمان آخرین اجرای/دریافت موفق در پیشخوان قابل تشخیص باشد.
- آزمون زنده روی `ahangban.ir` و Telegram از محیط توسعه انجام نشده است؛ عملکرد نهایی وابسته به Cron Job و دسترسی خروجی هاست است.
