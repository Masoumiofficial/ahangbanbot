# گزارش تحویل، ممیزی و تست — آهنگ‌بان v1.6.2

تاریخ بررسی: 2026-10-23  
مسیر فعال بررسی‌شده: Python polling؛ مسیر webhook PHP از منطق fallback جدا است.

## نتیجهٔ تست محلی

```text
PYTHONPATH=. .venv/bin/pytest -q
63 passed
```

همچنین `python3 -m compileall -q bot`، `git diff --check`، `node --check` برای JavaScript افزونه و Ruff منتخب (`E4,E7,E9,F`) روی handler/DB/voice/test files بدون خطا اجرا شدند؛ هر ۸ فایل PHP با `php-parser` و حالت PHP 7 parse ایستا شدند. این تست‌ها شامل منطق پایگاه دادهٔ پسند/دنبال‌کردن، بارگیری مشخصات فعلی از WordPress در فهرست‌ها، دکمه‌ها و صفحه‌بندی، فهرست کاربران ادمین، fallback صوتی mock، عدم retry پس از خطای مبهم و عدم fallback در وضعیت `queued` هستند.

این نتایج **تست زنده نیستند**: از محیط توسعه به WordPress/Telegram کانال واقعی وصل نشده‌ایم، کیفیت واقعی صدای خروجی روی کانال بررسی نشده و اجرای PHP/WordPress هاست انجام نشده است.

## پذیرش قابلیت‌ها

| قابلیت | نتیجهٔ پیاده‌سازی | قید ایمنی |
|---|---|---|
| Voice Note در Python polling | پاسخ موفق WordPress مقصد کانال و source URL واقعی `128`/`320` را فقط در وضعیت `unavailable`/`failed` ارائه می‌کند؛ Python با FFmpeg/libopus خروجی OGG/Opus می‌سازد و به پیام کانال reply می‌کند. | `queued` هرگز fallback نمی‌شود. یک فراخوانی ارسال انجام می‌شود؛ خطای شبکه/پاسخ مبهم retry نمی‌شود و به‌عنوان موفقیت گزارش نمی‌شود. فایل کامل به‌جای نمونه فرستاده نمی‌شود. |
| لایک آثار | دکمهٔ پسند/برداشتن پسند، شمارندهٔ کل کاربران ربات و فهرست شخصی صفحه‌بندی‌شده پیاده شد. دادهٔ ترجیح در SQLite است؛ اثر و اطلاعات آن از WordPress می‌آیند. | `user_id` و `post_id` مثبت؛ toggle تراکنشی؛ کلید یکتا مانع duplicate like می‌شود. دیتابیس آهنگ‌ها کپی نشده است. |
| دنبال‌کردن هنرمند | دنبال/لغو دنبال‌کردن با `term_id` واقعی، شمارندهٔ دنبال‌کننده‌ها و فهرست شخصی صفحه‌بندی‌شده پیاده شد. | اعلان خودکار انتشار در MVP وجود ندارد؛ فقط انتخاب کاربر در SQLite نگه‌داری می‌شود. |
| مدیریت کاربران | صفحه‌بندی فقط برای ادمین، با ID عددی، وضعیت فعال/مسدود، نام کاربری و آخرین فعالیت؛ `/block` و `/unblock` حفظ شده‌اند. | کنترل ادمین در callback و command انجام می‌شود؛ صفحه شامل کاربران ثبت‌شده در SQLite ربات است. |

## بررسی ایمنی و عملیات

- فایل‌های صوتی فقط با helper دانلود HTTPS محدودشده دریافت می‌شوند؛ همان اعتبارسنجی redirect/SSRF و سقف رسانهٔ موجود در ربات اعمال می‌شود.
- مقصد کانال فقط username معتبر یا شناسهٔ `-100…` پذیرفته می‌شود. تبدیل با آرگومان‌های مستقیم FFmpeg اجرا می‌شود، نه shell string.
- در نتیجهٔ مبهم `send_voice`، منبع جایگزین دیگری به Telegram فرستاده نمی‌شود؛ پیام نتیجه، بررسی کانال و عدم تکرار را صریح اعلام می‌کند.
- `Dockerfile`، FFmpeg را نصب می‌کند. برای deployment تازه یا کد به‌روز، image باید rebuild/redeploy شود. systemd host نیز به FFmpeg با `libopus` نیاز دارد.
- مسیر webhook/PHP همچنان به FFmpeg/libopus، `proc_open` و WP-Cron در WordPress وابسته است؛ Python fallback در webhook اجرا نمی‌شود.
- پسندها/دنبال‌ها در فایل SQLite ربات هستند و همراه volume یا backup همان فایل باقی می‌مانند؛ آن‌ها را به‌عنوان دادهٔ محلی کاربر پشتیبان‌گیری کنید.

## موارد خارج از اثبات

- تحویل واقعی Voice Note به کانال، دسترسی ربات/مجوز ارسال، URLهای رسانهٔ فعلی WordPress و WP-Cron روی هاست نیازمند آزمون عملی در محیط مالک سایت است.
- اتصال زندهٔ Telegram و WordPress، rebuild یا استقرار محیط تولید در این گزارش ادعا نمی‌شود.
- اگر WordPress وضعیت `queued` بدهد ولی اجرای WP-Cron بعداً شکست بخورد، Python fallback عمداً انجام نمی‌شود تا از Voice Note تکراری جلوگیری شود؛ این تصمیم مطابق معیار پذیرش MVP است.
