# رفع‌اشکال پاسخ‌ندادن `/start` در webhook — افزونهٔ v1.6.3

تاریخ بررسی: 2026-10-25
مسیر گزارش‌شده: WordPress webhook روی `ahangban.ir`
گزارش کاربر: API ربات `getMe` پاسخ می‌دهد، وب‌هوک ثبت است، اما `/start` پاسخی ندارد؛ `pending_update_count` برابر ۷ و آخرین خطای Telegram برابر `Connection timed out` است.

## تشخیص از روی کد و پیام خطا

- موفقیت `getMe` فقط تماس خروجی WordPress به Telegram را ثابت می‌کند؛ ثابت نمی‌کند Telegram توانسته درخواست ورودی POST را به WordPress تحویل دهد.
- `pending_update_count` و `last_error_message` در `getWebhookInfo` مربوط به تلاش Telegram برای تحویل update به URL وب‌هوک‌اند. `Connection timed out` می‌تواند از کندی پاسخ PHP/WordPress یا از شبکه، WAF/ModSecurity/Cloudflare و دسترسی inbound هاست باشد.
- در v1.6.2، callback وب‌هوک پیش از پاسخ HTTP، `process_update()` را کامل اجرا می‌کرد؛ `/start` در همان درخواست `sendMessage` را هم فراخوانی می‌کرد و timeout درخواست خروجی Telegram تا ۱۲ ثانیه بود. این پردازش هم‌زمان می‌توانست پاسخ webhook را از مهلت Telegram عبور دهد.
- بدون لاگ‌های زندهٔ سرور نمی‌توان تعیین کرد timeout گزارش‌شده حتماً از پردازش طولانی بوده یا از فایروال/شبکهٔ هاست؛ اصلاح کد مسیر پردازش هم‌زمان را حذف می‌کند، اما محدودیت inbound شبکه را دور نمی‌زند.

## اصلاح v1.6.3

- پس از بررسی Secret، اندازه و ساختار payload، update در جدول موجود WordPress ذخیره می‌شود؛ دیتابیس موازی یا فایل دیتابیس جدیدی ساخته نمی‌شود.
- کلید اصلی `update_id` مانع پردازش دوبارهٔ retryهای Telegram است. پس از ذخیرهٔ موفق، پاسخ کوتاه `200` برمی‌گردد و ارسال پیام در همان درخواست webhook انجام نمی‌شود.
- worker با WP-Cron update را پردازش می‌کند. وضعیت و خطاهای صف محلی از `pending_update_count` تلگرام جدا هستند؛ صفحهٔ «آزمون اتصال و وضعیت وب‌هوک» شمارنده‌های محلی، سن قدیمی‌ترین آیتم فعال و خطای `sendMessage` را نیز نشان می‌دهد.
- برای هر worker یک رویداد watchdog بعد از مهلت lock زمان‌بندی می‌شود تا اجرای ناقص پنهان نماند. رویداد پس از تکمیل عادی بی‌اثر است؛ اگر worker بعد از مهلت هنوز `processing` باشد، مورد `failed` ثبت می‌شود و به‌علت نامشخص‌بودن نتیجهٔ API خودکار replay نمی‌شود تا پیام تکراری نسازد.
- payload پس از موفقیت/شکست پاک می‌شود. درخواست‌های گیرکردهٔ بیش از دو روز منقضی می‌شوند؛ برای یک مورد `failed` نامطمئن، کاربر می‌تواند فرمان را دوباره بفرستد تا Telegram update_id تازه بسازد.

## روش بررسی پس از ارتقا — بدون Terminal

1. افزونهٔ v1.6.3 را در پیشخوان WordPress → افزونه‌ها نصب/جایگزین و فعال کنید. مهاجرت جدول هنگام اجرای افزونه خودکار است.
2. در «آهنگ‌بان API» روی «آزمون اتصال و وضعیت وب‌هوک» بزنید؛ شمارندهٔ Telegram را با صف داخلی WordPress مقایسه کنید.
3. یک‌بار `/start` را در گفت‌وگوی خصوصی ربات بفرستید. پس از پاسخ سریع webhook، worker باید پیام خوش‌آمد را بفرستد؛ در صورت خطای ارسال، جزئیات پالایش‌شدهٔ `sendMessage` در پیشخوان دیده می‌شود.
4. مسیر `https://ahangban.ir/wp-json/ahangban/v1/telegram/webhook` را می‌توان در مرورگر باز کرد؛ پاسخ GET فقط قابل‌دسترسی‌بودن مسیر عمومی را نشان می‌دهد و جای تست POST از سمت Telegram را نمی‌گیرد.
5. اگر Telegram همچنان صف pending/timeout نشان می‌دهد و صف محلی WordPress خالی می‌ماند، از پشتیبانی هاست بخواهید دسترسی inbound HTTPS POST از Telegram به همین مسیر، WAF/ModSecurity/Cloudflare و timeoutهای PHP-FPM را بررسی کند. اگر صف محلی رشد می‌کند یا سن آن زیاد می‌شود، WP-Cron و loopback requestهای WordPress باید بررسی شوند. Secret وب‌هوک را به پشتیبانی یا در پیام عمومی نفرستید.

## راستی‌آزمایی محلی و محدودیت

- این محیط به WordPress زنده، Telegram یا هاست `ahangban.ir` وصل نشده است؛ تحویل واقعی `/start` پس از انتشار افزونه ادعا نمی‌شود.
- `PYTHONPATH=. /tmp/ahangbanbot-venv/bin/pytest -q`: **۶۳ تست موفق**؛ `python -m compileall -q bot` نیز موفق.
- Ruff منتخب برای handler/DB/voice/tests موفق شد؛ موارد سبک قدیمی `E701`, `E722`, `F401`, `F841` از همان scope مستثنا شدند. `node --check` برای JS و `git diff --check` موفق‌اند.
- با `php-parser` و دستور زبان PHP 7.4، هر ۸ فایل PHP افزونه parse شد. این بررسی ایستا است، نه اجرای PHP یا WordPress.
- ZIP نسخهٔ 1.6.3 با `unzip -t` سالم بررسی شد؛ اندازه 72,028 بایت، SHA-256: `3d72ad6a3fdb69ff2aeeedaee196b990d1d9127612d1d27ec4e61a1497e230a5`.
- برای WP-Cron غیرفعال/مسدود، ارسال‌نشدن inbound POST، WAF و فایروال هاست نیاز به بررسی همان هاست یا پشتیبانی آن است؛ تغییر PHP به‌تنهایی نمی‌تواند اتصال شبکهٔ خارجی را تضمین کند.
