# گزارش ممیزی امنیت، کاربردپذیری و عملکرد — AhangBan v1.5.0

**تاریخ:** 2026-10-20

**دامنه:** افزونهٔ WordPress، کلاینت/ربات Python، پنل مدیریت و بستهٔ نصب افزونه

**وضعیت:** بازبینی ایستا و آزمون‌های محلی انجام شد؛ پذیرش زنده روی سایت/تلگرام انجام نشده است.

## خلاصه

در این نسخه، نگه‌داری Secretها در `wp_options` متوقف و اعتبارنامه‌های PHP به محیط پردازش PHP منتقل شده‌اند. احراز هویت API، rate limit، دریافت/ارسال رسانه، جلوگیری از پردازش تکراری updateهای Telegram، جست‌وجو و cache اصلاح شده‌اند. پنل WordPress فارسی و راست‌چین است و در موبایل واکنش‌گرا می‌شود. بستهٔ ZIP نصب‌پذیر ساخته و صحت آرشیو آن بررسی شده است.

این گزارش **گواهی امنیتی یا تأیید اتصال واقعی نیست**. در محیط توسعه، WordPress، دیتابیس سایت، حساب Telegram و PHP-FPM واقعی در دسترس نبوده‌اند؛ بنابراین SQL و رفتار hookها فقط از نظر ایستا/سازگاری نحوی بازبینی شده‌اند.

## تغییرها و کنترل‌های اعمال‌شده

### اعتبارنامه و API

- `AHANGBAN_API_TOKEN`، `AHANGBAN_BOT_TOKEN` و `AHANGBAN_BOT_SECRET` در افزونه فقط از متغیرهای محیطی PHP خوانده می‌شوند؛ Secretها در فرم مدیریت چاپ یا ذخیره نمی‌شوند.
- اجرای اول v1.5.0 گزینه‌های قدیمی این سه Secret را از `wp_options` حذف می‌کند. پیش از ارتقا باید محیط PHP آماده و از مقادیر/تنظیمات لازم نسخهٔ قبلی نسخهٔ پشتیبان تهیه شود.
- قالب API token در PHP دقیقاً ۶۴ رقم hex است و مقایسه با `hash_equals` انجام می‌شود. اگر Secret API در محیط PHP پیکربندی نشده باشد، مسیرهای محافظت‌شده موفقیت کاذب نمی‌دهند.
- اطلاعات Health عمومی به `{ "status": "ok" }` محدود شده است. CORS wildcard حذف شده؛ مسیرهای داده/کش Bearer token می‌خواهند، webhook هدر Secret تلگرام را بررسی می‌کند و وضعیت webhook به مدیر WordPress محدود است.
- ورودی جست‌وجو، شناسه، نوع اثر و pagination محدود/اعتبارسنجی شده‌اند؛ پردازش UTF-8 به `mbstring` وابسته نیست.

### نرخ درخواست و پراکسی

- شمارنده‌های API با upsert اتمی در جدول options **همان پایگاه‌دادهٔ WordPress** ثبت می‌شوند؛ token bucket فقط پس از تطبیق token معتبر افزایش می‌یابد و داده‌های قدیمی دوره‌ای پاک می‌شوند.
- IP پیش‌فرض از `REMOTE_ADDR` می‌آید. هدرهای forwarded فقط هنگامی پذیرفته می‌شوند که IP/CIDR اتصال با `AHANGBAN_TRUSTED_PROXY_IPS` تطبیق داشته باشد.
- updateهای Telegram نیز با شمارندهٔ اتمی per-user محدود می‌شوند؛ در خرابی DB سیستم fail-closed رفتار می‌کند.

### داده، جست‌وجو و cache

- endpointهای موسیقی فقط نوشته‌های publish را برمی‌گردانند که با `musics_type` یا کلیدهای واقعی رسانه در کد افزونه قابل‌شناسایی باشند. فیلتر نوع، آثار دارای فایل واقعی ولی بدون `musics_type` را هم در نظر می‌گیرد.
- مرتب‌سازی عنوان آثار هنرمند در SQL و پیش از صفحه‌بندی است. اتصال متای `song` به‌صورت یکتا انجام می‌شود تا چند ردیف متای هم‌نام باعث تکرار نتایج یا pagination نادرست نشوند.
- فهرست سبک هنرمندان cache می‌شود، تصویر فقط برای صفحهٔ درخواستی resolve و متای همان صفحه preload می‌شود. شمارش دسته‌ها در SQL انجام می‌شود و نوشته‌های غیرموسیقی در آن‌ها شمرده نمی‌شوند.
- namespace cache از transientهای وضعیت کاربر/ادمین جدا شده است؛ پاک‌سازی cache دیگر preview پیام همگانی یا stateهای ربات را حذف نمی‌کند. افزایش نسخهٔ cache اتمی است و با تغییر post/term و فیلدهای تصویر/شبکه‌های هنرمند invalidation انجام می‌شود.
- داده‌های آهنگ و هنرمند از دیتابیس اصلی WordPress می‌آیند؛ دیتابیس موازی برای محتوای سایت ساخته نشده است. جدول‌های تعامل ربات در WordPress و SQLite حالت Python فقط برای state ربات هستند.

### Telegram و رسانه

- درخواست‌های HTTP به Telegram روی HTTPS با SSL verification و redirect خاموش اجرا می‌شوند؛ Bot Token از طریق redirect به میزبان دیگری فرستاده نمی‌شود.
- timeout و پاسخ 5xx/3xx مبهم موجب resend کورکورانهٔ رسانه نمی‌شوند. updateهای Telegram با `update_id` به‌شکل اتمی deduplicate می‌شوند؛ مقدار صفر نیز معتبر است.
- URL رسانه باید HTTPS و عمومی باشد؛ URLهای دارای credential، مقصدهای محلی/خصوصی و redirect ناامن رد می‌شوند. دریافت fallback به‌صورت stream و با سقف 49 MiB انجام می‌شود؛ فایل موقت پس از تلاش پاک می‌شود و در صورت شکست، لینک واقعی منبع/صفحه استفاده می‌شود.
- انتشار خودکار کانال اختیاری و خاموش به‌صورت پیش‌فرض است؛ فقط post موسیقی تازه صف می‌شود. پیام broadcast دسته‌ای و با قفل/تأیید اجرا می‌شود.
- تنظیم حالت webhook در پنل، ثبت webhook را کنترل می‌کند. Python polling و WordPress webhook نباید برای یک Bot Token هم‌زمان فعال باشند؛ سرویس Python از پیشخوان راه‌اندازی نمی‌شود.

### پنل مدیریت و ربات Python

- پنل WordPress با RTL، طراحی واکنش‌گرا، وضعیت آماده‌بودن env بدون نمایش Secret، nonce، فرم POST/Redirect/GET، تأیید حذف webhook و کپی URL ارائه شده است.
- تنظیم bot در Python placeholderهای قابل‌اشتباه با مقدار واقعی ندارد. URL پایه باید HTTPS، بدون credential/query/fragment و با port معتبر باشد؛ localhost، دامنه‌های local شناخته‌شده و IP خصوصی/رزروشدهٔ صریح رد می‌شوند و HTTP client redirect را دنبال نمی‌کند.
- اجرای polling با پیکربندی نامعتبر fail-fast می‌شود و پیش از اعتبارسنجی، دیتابیس محلی ربات را ایجاد نمی‌کند. `/ping` و Health مدیر اطلاعات نسخهٔ داخلی سایت را نمایش نمی‌دهند.

## محدودیت‌ها و پذیرش باقی‌مانده

1. اتصال واقعی به WordPress/REST، بررسی متاها روی دیتابیس زنده، تنظیم env در PHP-FPM، webhook تلگرام، دسترسی کانال، WP-Cron و ارسال فایل روی هاست آزمایش نشده‌اند.
2. پشتیبانی هاست اشتراکی/DirectAdmin از متغیرهای محیطی PHP نامعلوم است. اگر PHP-FPM آن‌ها را دریافت نکند، webhook v1.5.0 کار نخواهد کرد؛ مقدار Secret را در `.env` ربات فرض نکنید که PHP خودکار می‌خواند.
3. عضویت اجباری کاربر در کانال در این نسخه پیاده‌سازی نشده است؛ اتصال کانال و انتشار خودکار دو قابلیت جدا هستند.
4. URL رسانه قبل از درخواست از نظر DNS عمومی/خصوصی بررسی می‌شود، اما اتصال شبکه به IP resolve‌شده pin نمی‌شود؛ تغییر DNS بین بررسی و اتصال به‌طور کامل حذف نشده است. برای `AHANGBAN_API_BASE` نیز DNS hostname resolve/pin نمی‌شود؛ این متغیر را فقط به میزبان API مورداعتماد تنظیم کنید. فیلدهای رسانه هم فقط باید توسط مدیران/منابع مورداعتماد تغییر کنند.
5. پیش از انتشار زنده: متغیرهای PHP را تنظیم، از تنظیمات نسخهٔ قبلی پشتیبان تهیه، مهاجرت حذف Secretها را بررسی، فقط یکی از polling/webhook را انتخاب، سپس `/start`، `/ping`، جست‌وجوی یک اثر واقعی، کاور/فایل واقعی، مجوز کانال و اجرای Cron را روی سایت آزمایش کنید.

**جمع‌بندی پذیرش:** بررسی‌های محلی و ساخت ZIP موفق‌اند؛ آماده‌بودن عملیاتی روی سایت واقعی هنوز تأیید نشده است.
