# بازبینی UX، اتصال کانال و باگ‌ها — v1.4.0

تاریخ: 2026-10-19 · شاخهٔ کاری: `arena/f2262129-ahangbanbot`

## تصمیم محصول: کانال + ربات

پیشنهاد من این است که کانال «ویترین/اعلان انتشار» باشد و ربات «جست‌وجو، جزئیات و دریافت اثر». برای شروع **عضویت اجباری** را فعال نمی‌کنیم؛ این کار ورودی ربات را محدود و تجربهٔ کاربر جدید را بدتر می‌کند. به‌جایش، هر اثر موسیقیِ تازهٔ واجد شرایط می‌تواند در کانال منتشر شود و یک deep-link کاربر را به همان کارت اثر در ربات برگرداند.

اتصال v1.4.0 به‌صورت opt-in آماده شده است: از پیشخوان وردپرس شناسهٔ کانال را تنظیم می‌کنید، پیام آزمایشی می‌فرستید و اگر مجاز بودید انتشار خودکار را روشن می‌کنید. **هیچ کانالی در کد حدس زده نشده و این قابلیت تا تنظیم صریح مدیر خاموش می‌ماند.** داده و تصویر کانال از همان نوشتهٔ منتشرشدهٔ WordPress می‌آید؛ دیتابیس جدا یا محتوای ساختگی ندارد.

## اتصال کانال، دقیقاً چه می‌کند؟

- ربات باید مدیر کانال با مجوز انتشار پیام باشد؛ `@username` برای کانال عمومی یا شناسهٔ `-100…` برای کانال خصوصی در پیشخوان وارد می‌شود.
- پیام «تست کانال» یک پیام واقعی می‌فرستد تا دسترسی نوشتن تأیید شود.
- auto-post پیش‌فرض خاموش است. پس از روشن‌کردن، فقط تغییر وضعیت پست تازه از غیرمنتشر به `publish` صف می‌شود و `musics_type` شناخته‌شده (audio/video/album) یا یکی از متافیلدهای رسانهٔ واقعی قالب (`music128`, `music320`, `album128`, `album320`, `video480`, `video720`, `video1080`) لازم است؛ نوشتهٔ معمولی نادیده گرفته می‌شود.
- ثبت صف از `wp_after_insert_post` انجام می‌شود تا ACF/metaهای موسیقی پیش از تشخیص نوع محتوا ذخیره شده باشند؛ سپس WP-Cron پست را می‌فرستد تا انتشار نوشتهٔ وردپرس منتظر درخواست Telegram نماند.
- پیام کانال عکس با وضوح مناسب، عنوان/خواننده و دکمهٔ صفحهٔ رسمی دارد؛ اگر یوزرنیم ربات در پیشخوان ثبت باشد، دکمهٔ «مشاهده و دریافت در ربات» هم اضافه می‌شود.
- deep-link در هر دو runtime `/start song_<post_id>` را می‌فهمد و با همان ID واقعی، اثر منتشرشده را از WordPress می‌خواند.
- اگر Bot API پاسخ مبهم/timeout بدهد، برای جلوگیری از پست تکراری retry کور انجام نمی‌شود؛ نیاز به بررسی مدیر دارد.
- WP-Cron باید فعال باشد؛ پست‌های قدیمی خودکار بازنشر نمی‌شوند. این تصمیم جلوی سیل پیام هنگام فعال‌سازی افزونه را می‌گیرد.

## مواردی که هنوز کم است (و شفاف نگه داشته شد)

1. جدول `favorites` و توابع DB در Python وجود دارند، اما دکمه/دستور کاربری کامل ندارند. آن قابلیت از فهرست «امکانات فعال» حذف شد؛ پیاده‌سازی درستش نیازمند parity در webhook و polling است.
2. عضویت اجباری کانال عمدی پیاده‌سازی نشده تا کاربر پیش از تجربهٔ ربات مجبور به عضویت نباشد. در صورت درخواست، باید جداگانه و اختیاری طراحی شود؛ برای `getChatMember` ربات باید مدیر کانال باشد.
3. ارسال فایل، پیام کانال، کیفیت واقعی فایل تصویر، نصب DB و WP-Cron روی سایت واقعی در این محیط قابل دسترسی نبودند؛ live success ادعا نمی‌شود.
4. بخش شمارش هنرمند SQL با PHP/WordPress runtime روی هاست واقعی باید پس از نصب سنجیده شود؛ در محیط توسعه فقط parser ایستا موجود است.

## شواهد تست محلی

- `python -m compileall -q bot` — موفق.
- `python -m pytest -q` با `bot/requirements-dev.txt` — **۲۶ تست موفق**.
- ساخت Application با credential ساختگی، بدون شبکه — گروه `-1`: یک middleware guard؛ گروه `0`: ۴۲ handler.
- همهٔ ۸ فایل افزونه با parser گرامر PHP 7.4 parse شدند. `php -l` واقعی و WordPress runtime در این محیط موجود نیست.
- `git diff --check` — موفق.

## پذیرش پیشنهادی پس از نصب

1. روی یک اثر واقعی منتشرشده، وضوح کارت را با نسخهٔ قبلی مقایسه کنید.
2. یک MP3 واقعی را ارسال کنید؛ بار دوم باید از file_id cache استفاده کند، یا در شکست، فقط پیوند واقعی منبع را بدهد.
3. دکمه‌های «جست‌وجوی خواننده»، بازکردن اثر و Home روی کارت عکس را امتحان کنید؛ پیام منو/کارت تکراری نباید ساخته شود.
4. اگر کانال می‌خواهید، ربات را مدیر کنید، تست را از پیشخوان بفرستید، سپس auto-post را روشن کنید و انتشار یک محتوای واقعی بعدی را بررسی کنید.
5. WP-Cron را برای زمان‌بندی کانال و broadcast بررسی کنید.

هیچ تست پذیرش زنده‌ای از این گزارش جایگزین اجرای مرحله‌های بالا نیست.
